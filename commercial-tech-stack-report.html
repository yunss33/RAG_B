标书多智能体项目商业可用技术选型报告

这份报告的目标不是罗列技术名词，而是帮你筛掉许可证风险、定下主框架，并明确这类项目为什么更适合 Python + Web 工作台，而不是单纯 Java 后端。结论上，这个项目建议采用 Python 作为 AI 与编排主后端，Next.js 作为人机交互前端，并尽量选择许可证更清晰的基础设施组件。

主后端：Python 前端：Next.js 向量库：Qdrant 数据库：PostgreSQL 缓存建议：Valkey 对象存储：谨慎评估 MinIO

一、组件许可证与商业可用性判断

组件 许可证 商业使用判断 建议 备注
Next.js MIT 可商用 推荐 前端生态成熟，适合工作台、多语言、预览与交互页面
FastAPI MIT 可商用 推荐 适合 AI API、任务编排接口、文件服务、Agent 网关
PostgreSQL PostgreSQL License 可商用 推荐 许可证宽松，企业级稳定，适合业务主数据库
Qdrant Apache 2.0 可商用 推荐 轻量、Docker 友好，适合 RAG 起步阶段
Valkey BSD 可商用 推荐 适合替代新版 Redis，许可证压力更低
Redis 近年许可证较复杂 需谨慎 可替换 能用，但商业合规判断不如过去简单，优先考虑 Valkey
MinIO AGPLv3 / 商业许可 需重点评估 谨慎使用 不是不能商用，但若你担心 AGPL 合规，最好先评估部署方式或换方案

二、底层框架选择：Python 还是 Java

推荐结论：主后端选 Python 你的核心问题是多智能体、RAG、文档解析、提示编排、证据绑定、内容生成与审查，这些都属于 AI 产品栈，Python 生态明显更强，也更快落地。
Java 不适合做这一期主控 Java 更适合传统中后台、重事务和企业集成。但你当前最重的是 AI 编排与文档智能，不是银行级交易链路。用 Java 做主干，会把很多 AI 相关开发成本抬高。
合理分工 Python 负责 Agent、RAG、文档处理、编排与任务流；Next.js 负责所有人机交互。以后真要接很多政企 Java 系统，再单独补 Java 集成层，而不是反过来。

三、为什么这个项目必须做人机交互

这不是“自动写文”工具

  • 标书里很多节点不能完全自动化，尤其是图片插入、资质选择、案例挑选、风险判断
  • 用户需要在关键节点确认，而不是等系统最后一次性吐出结果
  • 更好的形态是“Agent 工作台”，不是一个聊天框解决所有事情

四、推荐技术栈

层 推荐技术 为什么
前端工作台 Next.js 适合项目工作台、文件上传、流程进度、图片选择、HTML 预览、多语言界面
API 与项目服务 FastAPI 接口开发快，适合文件、任务、项目、审查结果等业务 API
多智能体编排 Python 自研 orchestrator 便于控制任务状态机、Agent DAG、人工确认节点和失败重试
Agent 执行层 Python 适合 Prompt、LLM SDK、检索工具调用、文档处理与规则审查
RAG 服务 Python + Qdrant 文档切片、Embedding、召回、重排、证据绑定都更适合 Python 生态
业务数据库 PostgreSQL 适合项目、章节、任务、引用、人工确认状态等结构化数据
缓存与队列 Valkey 用作队列、缓存、任务状态和锁，比新版 Redis 更省许可证顾虑
对象存储 对象存储服务 / 谨慎使用 MinIO 存招标文件、企业资料、图片、HTML 成稿、附件，注意许可证与部署方式

五、多语言能力怎么做

建议分两层

  • 界面多语言：前端 i18n，支持中文、英文，后续可继续扩
  • 内容多语言：标书正文按项目配置输出中文、英文或双语
  • RAG 层记录文档语言，写作 Agent 根据目标语言输出

六、MVP 必要页面

先做工作台

  • 项目创建页
  • 资料上传页
  • 招标解析结果确认页
  • 章节计划确认页
  • 图片候选选择页
  • 终稿预览页

七、最终建议

定型方案

  • 主语言选 Python
  • 前端选 Next.js
  • 缓存优先 Valkey
  • 向量库用 Qdrant
  • 部署先 Docker Compose
  • 坚持人机协作，不做全自动黑盒
